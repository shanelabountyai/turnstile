# turnstile

> **⚠️ Scope Honesty (read first).** Learning project, synthetic data only. The venue, the event, every customer and every command are generated by `tools/build_fixtures.py` from a seed; emails use `example.com`; nothing here has sold a ticket to a person. Payments run against **Stripe test mode** with test cards; no live key is ever configured, and the Stripe keys live only in the owner's local `.env` and Vercel project, never in this repository, the cloud build sessions or CI. CI proves webhook handling against **Stripe's documented signature scheme** with a fixture signing secret and recorded payloads; a live test-mode round trip is a by-hand step the owner runs and records in `docs/EVAL.md`. The engine proves agreement with the spec on 2,662 commands with 79 named traps; it does not prove the rules match any venue's house policy, any ticketing law (resale, fee disclosure, refund statutes), or any fire code. The reserved-seat model is one row of seats per section with an orphan rule; it is not a seat-map renderer. Screens and write-ups report what was measured against the oracle, never "never oversells" without the number and the stated conditions. Banner verbatim in the README.

> Cloned from saas-foundation v1.6.1. Port 7700. Upgrade with `npm run foundation:status`; template-owned paths are listed in the template's plan §3.2.

## Try the live demo (about ten minutes)

**The site is live** at **https://turnstile.labintelligence.co** (since 2026-11-21), behind a shared password that the
owner gives out; it is not written anywhere in this repository. The owner's deploy steps are in
[`docs/DEPLOY.md`](docs/DEPLOY.md), and the same walk runs locally from the Quickstart with [`docs/DEMO.md`](docs/DEMO.md).

Open **`https://turnstile.labintelligence.co/demo`**. The site asks for the shared password first (HTTP Basic, any username;
the owner gives it out). `/demo` then lists six seeded accounts: pick one to sign in, no email or password. **Start as
`owner@acme.demo.test`**: every step below uses it. Everything is
invented data. Payments are Stripe **test mode**: no real card works and no money moves. No email is sent.

| Account | Who | Used in |
|---|---|---|
| `owner@acme.demo.test` | owner of the venue's org; may also move the event clock | every step |
| `owner@globex.demo.test` | the same event in a second org with its own clock | the whole walk again, if `acme` is spent (see step 7) |

**Step 7 uses the demo up.** The event clock cannot be moved back past the last command, and sales close an hour after
doors, so once someone has done step 7 in an org, the Buy screen there says *Sales closed* for everyone after them.
If `acme` already says so, do the walk as `owner@globex.demo.test` in **Globex Labs**; if both do, the demo needs the
owner's reset (`docs/DEPLOY.md`, "Resetting the demo"). The database is shared and is not reset between visitors, so
counts and ledger totals include what earlier visitors bought.

**The dollar figures assume the event clock is more than 30 days before the show.** The Event page shows the event
clock; the show starts 2027-03-20 20:00. Closer to the show than that, steps 5 and 6 give a smaller refund or none,
by the refund windows on the Event page.

1. **Sign in and find the event.** Pick `owner@acme.demo.test` → **Acme Studio** → **Events** → **Synthetic Night
   (fixture)**. *You should see* two pools (a floor of 800, a balcony of 216) and four tiers, each with *remaining* and
   *available*, and the line **How “available” is worked out**: the smaller of what the tier has left and what its
   pool has left, worked out when the page loads and stored nowhere. The floor's tier allotments add up to more than the floor holds, on purpose.
2. **Hold two floor tickets.** **Buy** → *Acting as* → pick a customer nobody has used → **Act as**. There are 700
   (`C-0001` to `C-0700`): take one from the middle of the list, not the first. If the page then shows **Your holds**
   or **Your tickets**, an earlier visitor used that customer: pick another. The form starts on tier `EARLY`, quantity
   `1`: **change Tier to `ADV` and Quantity to `2`** → **Hold tickets**.
   *You should see* `OK HELD` and a ten-minute countdown. The countdown is display only; the server decides the expiry
   to the second.
3. **Pay with a Stripe test card.** **Pay $76.98** (2 × $34.99 + 2 × $3.50 fee). In the Stripe form use card
   `4242 4242 4242 4242`, any future expiry, any CVC → **Pay with Stripe (test mode)**. You come back to the Buy page;
   refresh until **Your tickets** shows one order with two ticket codes. The tickets are issued only when Stripe's signed
   webhook arrives, so a few seconds' wait is the design. Copy both codes.
4. **Two balcony seats, and the seat you cannot strand.** Change *Acting as* (at the foot of the page) to a second
   customer nobody has used. In a balcony row, tick two
   open seats with **one open seat between them** → **Hold seats in A**. *You should see* it refused: `ORPHAN_SEAT`,
   the seat in the middle would be stranded between two taken ones, and the page names that seat. Your two seats stay
   ticked: untick them, then tick two open seats **side by side**, hold them,
   and pay $127.00 (2 × $60.00 + 2 × $3.50) the same way. Copy one of the two codes.
5. **Refund one ticket at the box office.** **Box office** → *Refund a ticket* → your order (it carries your floor
   customer's id from step 2) → **Open order** → tick
   one ticket → **Preview refund**. *You should see* the days before the show, the window that applies, and the amount:
   more than 30 days out it is the full $38.49, fee included. **Refund $38.49**: the recorded refund equals the preview
   to the cent, and the ticket goes back into the pool.
6. **The ledger.** **Ledger**. *You should see* captured, refunded and net, one line per captured payment, and
   captured − refunded = net. If you are the first visitor since a reset: $203.98, $38.49, $165.49. **Download CSV**
   holds the same lines in integer cents.
7. **The door.** **Door** → paste the balcony code → **Check in**. *You should see* **DO NOT ADMIT**: doors are not
   open yet, they open at 2027-03-20 19:00. Now the one-way step: **Event** → *Event clock* → set it to
   20 March 2027, 7:00:05 PM (a 12-hour field shows `03/20/2027, 07:00:05 PM`; any time after 7 PM and before 8 PM
   works) → **Set clock**. Back on **Door**, the same code says **ADMIT**; scan it again and it is refused
   with the time of the first scan; of your two floor codes one is admitted and the refunded one is refused as refunded.

**What was checked, and where.** Steps 1 to 7 run as one browser session in `e2e/hosted-demo.spec.ts`, against a

A Next.js 16 + Prisma 7 + Postgres template with the parts every multi-tenant app rebuilds: magic-link sign-in with TOTP,

## Quickstart (about 10 minutes)

Needs Node 22 and a local Postgres 17 you can create databases in (Homebrew `postgresql@17` works with no password).

```bash
git clone git@github.com:shanelabountyai/saas-foundation.git my-app
cd my-app
git remote rename origin template
git checkout -B main v1.0.0   # -B: a fresh clone already has a main
npm ci
npm run new-project -- my-app 4200   # name and port; rewrites package.json, CI, Playwright, README
npm run db:setup                     # creates my_app and my_app_test, writes .env.local and .env.test, migrates both
npm run seed:demo                    # two orgs, owner/admin/member each; owners and admins have TOTP
npm run dev                          # http://localhost:4200/demo
```

**Do not use GitHub's "Use this template" button.** It drops the shared history, so later fixes can't be merged.
Working on the template itself: `npm run dev:template` serves on :4100.

`db:setup` never overwrites an existing `.env.*` and never prints a value. It uses your OS user against `localhost:5432`;
set `PGUSER`/`PGPASSWORD` or `LOCAL_PG_URL_BASE` for a different Postgres. Real keys (Resend, Stripe, Twilio) are optional
and go in `.env.local`; without them email is captured in the database, billing uses a mock, and SMS is off.

### Row-level security on Neon (optional, `RLS_MODE=enforce`)

`db:setup` gives you two roles locally: the owner (`DATABASE_URL` while RLS is off, `DATABASE_URL_SYSTEM`, `DIRECT_URL`) and
`<name>_app_rw` with `NOBYPASSRLS` (`DATABASE_URL_APP_RW`). To enforce locally, set `DATABASE_URL` to the app_rw URL and
`RLS_MODE=enforce` together: app_rw with RLS off sees no org rows, because off mode sets no org. On Neon, the role the console creates is a `neon_superuser` with `BYPASSRLS`, so the app role is made
in SQL, as the owner, on the branch:

```sql
CREATE ROLE app_rw LOGIN PASSWORD '<generate one>' NOBYPASSRLS NOSUPERUSER;
GRANT USAGE ON SCHEMA public TO app_rw;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_rw;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_rw;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT USAGE, SELECT ON SEQUENCES TO app_rw;
```

Then in Vercel: `DATABASE_URL` = app_rw through the pooler (`-pooler` host), `DATABASE_URL_SYSTEM` = the owner through the pooler,
`DIRECT_URL` = the owner without the pooler, `RLS_MODE=enforce`. Run `npm run rls:policies` once for your own org-owned models and
commit the migration; INV-30 fails until you do. The pooler accepts an SQL-created role (spike S4a ran through it).

## Commands

| Command | What it does |
|---|---|
| `npm test` | vitest against the local test database: unit, integration and all invariants |
| `npm run test:e2e` | Playwright against a production build (`E2E_DEV=1` runs the dev server for debugging one spec) |
| `npm run lint` / `typecheck` | ESLint (including the core-boundary rule) and `tsc` |
| `npm run db:migrate` | create a migration in dev; `db:migrate:test` applies to the test database |
| `npm run seed:demo` | idempotent demo accounts; refuses a cloud database |
| `npm run foundation:drift` | in a clone: fails if a template-owned file was edited |
| `npm run foundation:status` | in a clone: current vs latest release, and any `security:` changelog entries between |
| `npm run foundation:check-modules` | builds a scratch copy with both modules deleted (CI runs it) |

## Layout

- `src/core/`: env, db, auth, tenancy, authz, audit, tokens, email, share links, cron. Never imports from `src/modules` or `src/app` (lint-enforced).
- `src/modules/{billing,notifications}/`: optional, deletable.
- `src/app/`: routes. `src/app/cron-jobs.ts` is where a clone adds its own cron work. `src/app/org-hooks.ts` holds the
  clone's org hooks: `beforeOrgDelete` (runs before an org is deleted; throwing stops it) and `filterListedOrgs` (which of a
  user's orgs `/onboarding` and `/demo` list; default all, and it can only hide, never add — D-22).
- `prisma/schema/`: `core.prisma` plus one file per module. A clone's tables get their own file and migrations.
- `tests/invariants/`: the security rules as tests. `tests/fixtures/app.ts` holds a clone's harness rows.

## Removing a module

Delete the paths listed for it in `scripts/foundation-modules.ts`, and the lines marked `// billing` or `// notifications`
(`{/* billing */}` in `layout.tsx`) in `prisma/schema/core.prisma`, `src/app/cron-jobs.ts` and `src/app/o/[org]/layout.tsx` —
that includes the module's nav link, so it goes with the rest.
`foundation:check-modules` does exactly this in a scratch copy (`removeModule()` in `scripts/foundation-modules.ts`) and
requires validate, typecheck, the module-tooling unit tests, build and drift to pass.
The module's tables stay in the migration history; drop them with a clone migration if you want them gone. Date that
migration after the template's newest migration: the RLS policy migrations up to `20261108000002` `ALTER` module tables
unguarded. Policy migrations from 1.6.2 on skip a module table that no longer exists.

If your own code imports a module outside the marked lines (a clone's own routes or lib files, not just
`cron-jobs.ts`/`org-hooks.ts`), list it in `src/app/required-modules.ts`. `check-modules` leaves a required module in
place and still removes the rest.

## Staying current

Template-owned paths (core, modules, invariants, security routes) are never edited in a clone, so `git merge vX.Y.Z` is clean.
An urgent local patch goes in `FOUNDATION_PATCHES.md` as `` `path` `hash` — reason `` (drift prints the hash to paste in) and moves upstream at the next release. The excuse stops matching, and drift fails again, once that path changes further.
Upgrade steps and versioning rules: `IMPLEMENTATION_PLAN.md` §3.3.
