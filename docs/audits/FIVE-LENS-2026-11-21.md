## 3. Proposed PRD set

Titles, goals and acceptance tests only. Full PRDs after Shane approves.

### PRD-1 Money boundary before O-8 (items 1, 2, 4, 7)
**Goal:** Stripe and the ledger never disagree on the walk, in either org, including after a decline.
**Acceptance tests**
- A test casts the first refund in two events (two orgs). The gateway receives two different idempotency keys. A retry in the same event sends the same key.
- The same holds for the first waitlist offer's PaymentIntent (`O-0001`) in two events.
- A recorded test: `PAY_FAILED` that returns `PAYMENT_FAILED_RELEASED` calls `paymentIntents.cancel` on that PaymentIntent. A later `payment_intent.succeeded` for it creates no order.
- After a card error, the pay form does not submit again on the same client secret (component test or e2e).
- A gateway that throws a Stripe connection or API error on refund: the action returns a result, does not throw; the Refund row keeps `stripeRefundId` NULL; the next row is still tried; the screen says "Refund recorded; Stripe will be told". An idempotency error is logged as a bug.
- Webhook: an unsigned POST gets the same 400 whether or not its `event_id` exists, with no database read. A signed event with no `metadata.event_id` gets 200 "ignored". A non-UUID `event_id` never returns 500.
- `inventory:eval` still matches 2,662 commands; `fixtures:check` and `inventory:lint` OK; no fixture changes.
- O-8 recorded in `docs/EVAL.md`: one 4242 order, one refund in `acme` and one in `globex`, and one decline then 4242 on the same hold, with ids.

### PRD-2 Demo safe to share (items 3, 5, 6, 8, 20)
**Goal:** a visitor with the password cannot break the demo for others, does not hit a crash, and finds the README matches the screen even when they are not the first.
**Acceptance tests**
- With `DEMO_MODE=1`, a demo owner's POST to `/o/acme/settings/{danger,members,sso,apikeys}` gets 403 and the org still exists. Without `DEMO_MODE`, template behaviour and tests are unchanged.
- `foundation:drift` stays clean (the change lives in clone-owned `src/proxy.ts` / `src/checkout/gate.ts`).
- A member on the event page sees no active Set clock form, and a sentence says who can move the clock. Posting the action directly returns an inline refusal; the org bar stays; no HTTP 500.
- e2e runs the README walk twice on one database, the second time as a different fresh customer per the README, and every "you should see" check passes both times.
- `deploy-env` refuses a `DEMO_ACCESS_PASSWORD` under 16 characters, with the name only, never the value.
- `docs/decisions.md` has a row on who may refund, sell and check in.

### PRD-3 Live payment and refund resilience (items 9, 10, 11, 12, 18)
**Goal:** the money steps degrade to plain words, never to the error page, and a spent or expiring demo says what to do next.
**Acceptance tests**
- A `PAYING` hold whose PaymentIntent is `processing` or `succeeded`, or a return with `redirect_status=succeeded`, shows "Payment received by Stripe…" and no card form.
- `createPaymentIntent` throwing leaves the hold `HELD` and shows an inline message. A `clientSecret` failure on Buy affects only that hold's pay form.
- `payStart` on a stored-`HELD` hold that has expired by the event clock calls no Stripe method.
- On `VERCEL_ENV=production` with no `STRIPE_SECRET_KEY`, `stripeGateway()` throws.
- The clone cron settles every Refund row with NULL `stripeRefundId`; the Ledger shows a count of unsettled refunds.
- With the clock past `sales_close_at` in demo mode, the Events card and the Buy screen show the "used up; use globex or ask for a reset" line above the customer picker.
- Set clock to a time past `sales_close_at` in demo mode asks for confirmation and shows the one-way warning.
- `hosted-demo.spec` sets the event clock itself and runs the hold/release branch whatever the wall date.
