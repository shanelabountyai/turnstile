# PRD: Turnstile — Event Venue Ticketing with Capacity That Cannot Lie

**Sample business:** "The Foundry Hall," an invented 1,016-seat venue (synthetic): a general-admission floor of 800 sold in three price tiers whose allotments add up to 900, and a reserved 216-seat balcony in three sections; one event, one on-sale window, timed cart holds, Stripe test-mode checkout, waitlists with timed offers, a refund policy as data, and door check-in
**Build log:** #13 Event Venue / Ticketing, main track. Chips: capacity · waitlist · refunds
**Status:** Draft v1.0 — kickoff kit, oracle run and traps verified (see `docs/decisions.md` §Review log)
**Learning objectives:** inventory that is correct under competition for the last seat: a shared pool with over-allotted tiers, timed holds that expire at a second, the hold-versus-webhook race (the payment that lands after the hold died), reserved seats with an orphan-seat rule, a FIFO waitlist whose head is never skipped, refund windows and fee rules as data with integer rounding, idempotent webhooks, and door check-in that refuses a second scan. Plus the operational honesty the card asks for: "available" is a derived number with a stated formula, never a column somebody edits.

**Positioning note:** orgs, roles, audit and the outbox are foundation work; integer money, calendar-string dates, append-only tables, a pure engine with a lint, and frozen fixtures with a stdlib oracle are ported from siblings (`docs/portfolio-overlap.md`). The lesson is the inventory engine (`src/inventory/`) and the Stripe boundary around it (`src/checkout/`). Gavel already taught N-writer row-lock contention; Turnstile does not re-teach it, it proves the *rules* under one serialized stream and then puts a short lock around the cast path in Phase 2.

`docs/decisions.md` outranks this document wherever they differ.

## ⚠️ Scope Honesty (read first)

Learning project, synthetic data only. The venue, the event, every customer and every command are generated by `tools/build_fixtures.py` from a seed; emails use `example.com`; nothing here has sold a ticket to a person. Payments run against **Stripe test mode** with test cards; no live key is ever configured, and the Stripe keys live only in the owner's local `.env` and Vercel project, never in this repository, the cloud build sessions or CI. CI proves webhook handling against **Stripe's documented signature scheme** with a fixture signing secret and recorded payloads; a live test-mode round trip is a by-hand step the owner runs and records in `docs/EVAL.md`. The engine proves agreement with the spec on 2,662 commands with 79 named traps; it does not prove the rules match any venue's house policy, any ticketing law (resale, fee disclosure, refund statutes), or any fire code. The reserved-seat model is one row of seats per section with an orphan rule; it is not a seat-map renderer. Screens and write-ups report what was measured against the oracle, never "never oversells" without the number and the stated conditions. Banner verbatim in the README.

## Problem Statement

Ninety minutes before doors the box office sees "87 Door tickets left" on the tier card, the floor is already at 800 bodies' worth of sold and held tickets, and the person at the window has a card out. Ticketing is mostly arithmetic that has to be right at the edge: the tier allotment that lies when the pool is full; the cart hold that expired one second ago; the payment webhook that arrives after the hold timed out and the seat went to someone else; the two adjacent balcony seats that nobody can buy because somebody took the one between them; the waitlist where the fourth person in line gets offered the pair because the first three wanted four; the refund that pays back 49.99% because somebody rounded; the second scan of a screenshot at the door.

Turnstile treats the event as one ordered stream of commands evaluated by a pure engine that gives the same answer in any arrival order, with every outcome from a closed vocabulary and every number derived, not stored. The builder lesson: the trust problem in ticketing is not fraud detection, it is that "available" is a *formula over three states and a clock*, and the system has to compute it the same way at the tier card, the seat map, the checkout button and the door.

## Goals

1. **The pool is the truth.** A tier's availability is `min(allotment − sold − held, pool capacity − pool sold − pool held)`, derived on every read; the fixture ends with Door showing 87 of allotment left and 0 available, and `SOLD_OUT_POOL` is a distinct code from `SOLD_OUT_TIER` so the UI can say which one it was.
2. **Holds are timed to the second and the engine is pure.** `src/inventory/` imports no database, clock, randomness, network or model client; `expires_at <= at` expires; the same commands in any order give the same tables and the same commitment, proven by shuffling.
3. **The hold-versus-webhook race is a rule, not a bug report.** A hold in `PAYING` is not expired by the cart TTL; it times out on its own clock; a success webhook after the timeout is `PAID_AFTER_TIMEOUT`: full refund, no tickets, inventory already released. Webhooks are idempotent (`PAYMENT_DUPLICATE`).
4. **Reserved seats with an orphan rule and a shape-aware waitlist.** A hold that would strand a single seat between two taken seats is `ORPHAN_SEAT` (row ends excepted); a section waitlist is served only when a contiguous block fits; "12 seats remaining" can honestly mean "0 sellable to anyone waiting."
5. **The waitlist is FIFO and the head blocks.** Nobody behind the head is offered inventory the head could not use; an offer is a timed hold; an ignored offer is dropped (`DROP`) and the next head is offered in the same tick; the wrong customer cannot accept an offer.
6. **Refunds are policy as data with integer rounding.** Windows in whole days before the start on one calendar axis; `price × bps / 10000` floored; the fee refunded or kept per window; a refunded seat returns to the pool and may be offered to the waitlist; cancellation refunds everything including fees, including checked-in tickets.
7. **(Builder goal)** Say what the numbers mean: the fixture proves agreement with the spec on 2,662 commands, 152 rejects over 35 codes and 79 named traps, by the same author; it does not prove the policy is a good policy or that the orphan rule matches any venue's.

## Non-Goals

- **Reserved-seat map rendering, pricing zones within a section, accessible-seat logic.** Sections are rows of numbered seats; seat selection is a list of ids. Seam only.
- **Resale, transfer between customers, dynamic pricing, promo codes, bundles, taxes.** Prices are tier constants; one service fee per ticket.
- **Live Stripe keys, Stripe Connect, payouts, chargebacks/disputes.** Test mode only; a dispute is a P1 seam.
- **Multi-event scheduling, recurring events, venue maps across events.** One event per org in Phase 1–3; the model allows more, the UI shows one.
- **Door hardware, QR scanning camera UI.** Check-in takes a ticket code typed or pasted; the code is a stable hash, not a signed JWT (P1).
- **Row-lock contention tests at scale.** Gavel owns that lesson; Phase 2 uses one short transaction per cast with a per-pool advisory lock and a single test that two concurrent casts for the last seat produce one `HELD` and one `SOLD_OUT_POOL`.
- **Skipping the waitlist head (`SKIP_TO_FIT`).** Named, refused by the schema (`RULES_INVALID`), P1 if ever.
- **Sending anything.** Order confirmations and offer notices go to the outbox and stop there.

## Requirements — Must-Have (P0)

**P0-1: Event, pools, tiers, sections, rules as data**
- [ ] `event.json` schema (closed enums for pool kind, waitlist rule, offer-expired rule; refund policy sorted descending and ending at 0 days; reserved pool capacity equals its seat count; tiers may over-allot a pool) validated with `RULES_INVALID` naming the field (GT-13)
- [ ] Seats minted from sections as `<section>-<row>-<nn>`; one tier per reserved pool

**P0-2: Inventory engine, pure** *(core learning artifact #1)*
- [ ] `src/inventory/`: hold rules H-1..H-14, payment rules P-1..P-8, waitlist rules W-1..W-7, refund rules R-1..R-6, check-in rules C-1..C-4, cancellation X-1..X-4 (brief §4–§8); no forbidden import (`inventory:lint`)
- [ ] Commands evaluated in `(at, cmd_id)` order whatever order they arrive; `advance(at)` expires holds and offers and times out payments *before* the command at `at` is evaluated (GT-04, GT-08, GT-10)
- [ ] GT-01..GT-18 pass in TypeScript with the exact values in the brief
- [ ] Order independence: a vitest shuffles `commands.csv` 20 times and asserts identical tables and commitment

**P0-3: Capacity math** *(core learning artifact #2)*
- [ ] `available(tier) = min(tier_remaining, pool_remaining)` with `held` counting `HELD` and `PAYING` holds and offers; `SOLD_OUT_POOL` checked before `SOLD_OUT_TIER` (H-11, H-12)
- [ ] Refunded tickets return to the pool and to their tier, even an off-sale tier, so another tier can sell the seat (GT-03c/d)
- [ ] Orphan rule: `ORPHAN_SEAT` when the hold increases the row's orphan count; row ends and filling a single never do (GT-05); switchable by `prevent_orphan_seats`

**P0-4: Holds, payments, the race** *(core learning artifact #3)*
- [ ] Client-supplied hold ids (`HOLD_ID_DUPLICATE`), TTL to the second, `RELEASE` by the owner only (`HOLD_NOT_YOURS`), closed hold states
- [ ] `PAY_START` moves a `HELD` hold to `PAYING` with its own timeout; `PAY_SUCCEEDED` on `PAYING` → `CONFIRMED` + tickets; on `PAY_TIMEOUT` → `PAID_AFTER_TIMEOUT` refund; on `CANCELLED` → `PAID_AFTER_CANCEL` refund; any webhook on a settled payment → `PAYMENT_DUPLICATE` no-op (GT-08, GT-11, GT-12)
- [ ] Amount = `qty × (price + fee)`; price is the tier price at hold time

**P0-5: Waitlist with timed offers** *(core learning artifact #4)*
- [ ] Join only when the target cannot serve you now (`WAITLIST_NOT_NEEDED`); one active entry per customer per target; GA target = tier, reserved target = section
- [ ] `HEAD_BLOCKS` fill after every inventory return: the head is offered when it fits (GA: `available ≥ qty`; reserved: lowest contiguous block that passes the orphan rule), then the next head against what is left; an offer is a hold of kind `OFFER` with the offer TTL; expiry drops the entry and re-fills in the same tick (GT-09, GT-10)
- [ ] A GA tier going off sale closes its waiting entries (`CLOSED_OFF_SALE`, W-5)

**P0-6: Refunds and cancellation** *(core learning artifact #5)*
- [ ] `days_before = floor((starts_at − at) / 86400)` on the one axis; first policy row with `min_days_before ≤ days_before` applies; `refund_bps = 0` → `REFUND_WINDOW_CLOSED`; amount `price × bps // 10000 (+ fee if fee_refunded)`; per ticket; `TICKET_CHECKED_IN` and `TICKET_ALREADY_REFUNDED` refused (GT-06, GT-07, GT-16)
- [ ] `CANCEL_EVENT`: every live ticket refunded at `cancellation_refund_bps` plus fee, holds cancelled, waitlists closed, every later command `EVENT_CANCELLED` except late webhooks; net cents 0 on the golden (GT-11)

**P0-7: Check-in**
- [ ] `CHECK_IN` by ticket id/code: `TICKET_UNKNOWN` → `TICKET_REFUNDED` → `DOORS_NOT_OPEN` → `ALREADY_CHECKED_IN` (with the first scan time) → `CHECKED_IN` (GT-16)

**P0-8: Evaluation** *(the measured claim)*
- [ ] `npm run inventory:eval` prints the brief §11 table and diffs every row of the seven `expected_*` files; exits non-zero on any difference
- [ ] `npm run fixtures:check` = `verify_fixtures.py && golden_answers.py && git diff --exit-code fixtures/`
- [ ] `docs/EVAL.md` holds the table as measured by TypeScript, the fixture hashes, and the D-24 wording

**P0-9: Schema, Stripe boundary, append-only storage (Phase 2)** *(core learning artifact #6)*
- [ ] `Event`, `Pool`, `Tier`, `Section`, `Seat`, `Hold`, `Payment`, `Order`, `Ticket`, `WaitlistEntry`, `Refund`, `CommandLog` per D-20..D-23; `Hold`, `Payment`, `Ticket`, `Refund`, `CommandLog` append-only via triggers (state changes are new rows or a single guarded status column, D-21)
- [ ] Cast path: one transaction per command, `pg_advisory_xact_lock(pool)` around the availability read and the write; a test with two concurrent casts for the last seat yields exactly one `HELD`
- [ ] Stripe: `PaymentIntent` created at `PAY_START` with `idempotency_key = hold_id`; webhook route verifies `Stripe-Signature` (t + v1 HMAC-SHA256, 5-minute tolerance) with **fixture payloads and a fixture secret in CI**; `event.id` deduplicated in `CommandLog`; refunds issued as Stripe refunds against the PaymentIntent, idempotency key = refund id; a `payment_intent.succeeded` after timeout triggers the refund automatically
- [ ] `npm run inventory:eval:db`: the 2,662 commands through the cast path with Stripe mocked at the HTTP boundary (recorded fixtures), then a recount from stored rows equals the Phase 1 engine

**P0-10: Views (Phase 3)**
- [ ] **Event:** pool and tier cards with the formula visible on hover (remaining vs available); on-sale windows; rules read-only
- [ ] **Buy:** GA quantity or balcony seat picker (rows as lists), hold countdown, Stripe Elements test checkout, order with ticket codes; waitlist join and offer acceptance with its countdown
- [ ] **Box office:** window sale against the same engine; waitlist per target with positions; refunds with the computed amount and window shown before confirming
- [ ] **Door:** check-in by code with the four refusals spelled out; live count
- [ ] **Ledger:** captured, refunded, net; per order; exportable CSV

## Phasing

## Risks

- **Spec optimism.** The oracle agrees with itself. Mitigation: D-24 wording; O-items for every policy choice; a hand-written scenario in P1 (the cancelled event).
- **Stripe in a public repo.** Mitigation: D-5/D-6; `.env.example` only; CI has no Stripe key and does not need one; `git ls-files` secret grep before the first push; the webhook secret in CI is the fixture's, published on purpose.
- **"Held" counting makes the pool look fuller than it is.** Mitigation: by design (a held seat is not for sale); the card shows sold, held and available separately; expiry is to the second.
- **Orphan rule is wrong for a real venue** (some allow aisle singles, some forbid any single). Mitigation: it is one boolean now, an O-item, and the rule function is 20 lines with GT-05 pinning it.
- **Cloud sandbox cannot run Prisma, Playwright or reach Stripe.** Mitigation: D-7; Phase 1 needs none of them; Phase 2 uses recorded Stripe fixtures; CI decides.
- **Clamped background commands in the fixture** (154 background commands were moved to the current second of a running multi-step trap by the generator, D-19). Mitigation: stated; it changes timestamps, not rules; the shuffle proof covers ordering.
